# Коммиты, preview и релизы

## Conventional Commits

PR title проверяет `amannn/action-semantic-pull-request` со стандартными типами.
Примеры: `feat(map): добавить слой`, `fix(ui): исправить попап`,
`feat!: изменить формат настроек`. Scope и русское описание допустимы.
В main попадает squash с заголовком и описанием PR; соавторов в описание добавляет агент по AGENTS.md.

Release Please анализирует изменения после последнего стабильного тега:

| Изменения                                                         | Результат из 0.15.1                  |
| ----------------------------------------------------------------- | ------------------------------------ |
| fix, perf                                                         | 0.15.2 (patch)                       |
| feat                                                              | 0.16.0 (minor)                       |
| ! в заголовке или BREAKING CHANGE в теле коммита                  | 1.0.0 (major), включая версии до 1.0 |
| Только docs, chore, ci, build, test, refactor, style без breaking | Нет выпуска                          |

Выбирается максимальный bump диапазона. Обе настройки уменьшения bump до 1.0
отключены. Описание PR переносится в squash-коммит вместе с trailers. Breaking change обозначать `!` в PR title; явный `BREAKING CHANGE` в описании также сохраняется.

## Тестовая сборка в PR

После успешного `check` для внутренних PR, кроме Dependabot, CI собирает
`dist/debug/sbg-vanilla-plus.user.js`. `actions/upload-artifact` сохраняет ровно
этот файл в ZIP на 14 дней. Отдельный job `preview-comment` с
`mshick/add-pr-comment` добавляет ссылку, SHA ветки, SHA merge commit и ссылку на run.

Сборка имеет только `contents: read`. Job комментария имеет
`pull-requests: write`, не делает checkout, не скачивает и не исполняет код PR.
ID artifact и комментария включают run/attempt: один комментарий на попытку.
Ошибка новой сборки не добавляет комментарий; старые комментарии остаются историей.
Rerun старого запуска сохраняет собственный SHA и не заменяет ссылку нового.

Для установки войти в GitHub, скачать и распаковать ZIP, импортировать
`.user.js` в менеджер юзерскриптов. Выключить stable на время проверки,
после неё выключить debug и вернуть stable. Debug работает без сервера,
содержит inline source map и не обновляется автоматически.
Ссылка действует 14 дней, если artifact или run не удалены раньше.
Интерактивные проверки игры выполняет пользователь.

## Ручные notes в release PR

Финальный источник пользовательских notes - блок между `<!-- release-notes:start -->`
и `<!-- release-notes:end -->` в описании существующего release PR. Release Please
управляет версиями и первоначальным описанием PR; его список коммитов служит
материалом для сверки. Комментарий "Релизные заметки" с маркером
`<!-- release-notes:v1 -->` хранит предварительные формулировки и подтверждения.

При создании и обновлении release PR workflow Release создаёт комментарий из
`.github/RELEASE_NOTES_TEMPLATE.md`, если его ещё нет. Существующий комментарий
сохраняется без перезаписи. Учитываются комментарии владельца, участников,
сотрудников репозитория и github-actions[bot]; неоднозначность останавливает подготовку.

Подтверждённый пользовательский эффект добавляется в черновой комментарий сразу.
Автоматический черновик и все коммиты диапазона нужно сверить с итоговым кодом;
CI не доказывает смысловую полноту текста.

Перед подготовкой материалов согласовать с пользователем полный текст описания PR.
Сначала показать проект notes и дать пользователю внести правки; после его редактуры
повторно проверить формулировки и получить явное подтверждение публикации полного
описания. Заменить автоматический список изменений финальным русским текстом
между маркерами, без собственного заголовка версии. Сохранить заголовок версии
`## [X.Y.Z]`, разделители `---`, служебные начало и конец описания, заголовок PR
и метки бота. Блок notes размещается после заголовка версии внутри раздела релиза.
Доказательства и результаты проверок остаются в черновом комментарии.

Release Please продолжает обновлять PR обычным образом и может перезаписать
отредактированное описание. После обновления ботом проверить версию, диапазон
изменений и финальный блок: при его потере или изменении восстановить и согласовать
текст, затем заново подготовить материалы. Отдельной блокировки бота нет.

Похожие PR объединять в один пункт по пользовательской фиче или общей области
изменений, например обновления библиотек. Писать очень коротко: одна короткая фраза
на группу, без деталей реализации. Сохранять существенные условия исправлений;
после фразы ставить прямые ссылки на все относящиеся PR.

Проверить каждый PR полного диапазона, включая коммиты без Conventional Commits:
для него должна быть группа либо обоснованное исключение. Обновления зависимостей
не исключать автоматически: проверить diff, сопутствующие правки и подтверждённый
пользовательский эффект. Внутренние изменения без пользовательского эффекта
не включать. Краткость текста не заменяет полноту проверки.

## Общие команды

Node.js 24; команды выполняются из корня репозитория. Для записи нужен
`GH_TOKEN` или `GITHUB_TOKEN` с доступом к этому репозиторию. Не выводите токен.
Команды чтения публичного репозитория могут работать без токена.

```powershell
node scripts/releaseNotes.mjs inspect
node scripts/releaseNotes.mjs ensure
node scripts/prepareRelease.mjs 60
node scripts/releaseNotes.mjs check 60
```

Номер 60 - пример: фактический номер показывает `inspect`. Без номера выбирается
единственный открытый release PR бота в main; отсутствие или несколько PR - ошибка.
`inspect` ничего не меняет. `ensure` создаёт только отсутствующий черновой комментарий
и проверяет готовность финального описания. Публикация комментария или правка
описания агентом требует прямого разрешения пользователя после показа полного текста.

Перед локальной подготовкой получить актуальную ветку release PR, установить
зависимости и проверить рабочее дерево. `prepareRelease.mjs` выполняет команды
проекта из `.github/release-notes.json`, формирует `RELEASE_NOTES.md` из финального
блока описания и `.release-notes.json` со схемой 2, версией, базой main и хешем notes,
а также хешем всех исходников и материалов, кроме двух выходных файлов notes.
Первая ошибка останавливает цепочку. Файлы notes являются результатом генерации:
исправлять источник в описании PR и повторять подготовку. Снимки прежней схемы 1
не принимаются: после перехода с комментария требуется новая подготовка.

Локальная команда оставляет материалы для проверки diff и коммита в той же ветке.
Она не выполняет merge, не создаёт тег и не публикует релиз. После push проверить CI.

То же доступно без агента: **Actions / Prepare release / Run workflow** на main.
Workflow проверяет release PR, готовит материалы и выполняет проверки с токеном
только для чтения. Отдельный job из main принимает только разрешённые файлы,
проверяет актуальность финальных notes, main и head, затем добавляет коммит в ту же
ветку без force push. Код из PR и скачанных материалов с write-токеном не исполняется.

## Готовность и выпуск

| Состояние  | Условие и переход                                                                                 |
| ---------- | ------------------------------------------------------------------------------------------------- |
| Черновик   | Финальный блок в описании отсутствует, пуст или содержит TODO; требуется редактура и согласование |
| Подготовка | Общая команда генерирует notes и материалы, выполняет проверки                                    |
| Готово     | Текст, версия, main и содержимое соответствуют сохранённой подготовке                             |
| Устарело   | Изменились финальные notes, версия, main или материалы; повторить подготовку                      |
| Выпуск     | Ручной squash merge готового release PR запускает существующую публикацию                         |

Правки чернового комментария и текста вне финального блока не меняют готовность.
Workflow Release notes перечитывает описание при изменениях PR.
Он публикует commit status `check`, который дополняет существующий обязательный
check run с тем же именем: должны пройти оба. Для нового head успешная полная
подготовка через Actions также выставляет статусы остальных обязательных проверок.
Это нужно, поскольку изменения через GITHUB_TOKEN не запускают обычный PR CI,
а check runs от workflow_dispatch не удовлетворяют защите PR.

Перед merge просмотреть фактический diff notes, версий и материалов; подтвердить
все необходимые проверки. После squash merge publish повторно сверяет описание PR,
notes и хеш содержимого с точным SHA выпуска до сборки и перед публикацией.
Изменение main между подготовкой и merge тоже останавливает выпуск.
Подпись, проверка assets, загрузка и запрет перезаписи опубликованных assets
продолжают действовать по процессу проекта. Подготовка сама по себе выпуск не разрешает.

## Для агентов

При любом запросе о выпуске или дополнении notes сначала прочитать этот документ
и выполнить `inspect`: использовать найденный release PR, его описание и черновой комментарий.
`AGENTS.md` и release-скиллы ссылаются на этот процесс; отдельные копии алгоритма
и дополнительные хранилища заметок не создаются. Изменение команд, CI и документации
должно сопровождаться проверкой их согласованности и тестами переходов состояний.
Изменения релизного процесса и скиллов оформлять отдельным PR; дождаться его
вливания в main, затем готовить релиз по актуальным инструкциям.
Агент выполняет доступные ему действия, включая GitHub, с отдельным подтверждением
публикации текста, запуска Prepare release и merge. Согласование плана и редактуры
notes не разрешает эти действия автоматически.

## Подготовка и публикация

1. Обычные PR проходят проверки и squash merge в main. На push main workflow
   Release создаёт или обновляет один release PR через Release Please.
   Стратегия node обновляет `package.json`, `package-lock.json` (включая
   `packages[""].version`) и `.release-please-manifest.json`.
   `skip-changelog: true`: автоматический черновик остаётся в теле PR.
2. Собрать черновик в комментарии "Релизные заметки" существующего release PR.
   Сверить диапазон изменений и итоговый код по [правилам текста](agent/release.md).
   Дать пользователю отредактировать notes, согласовать финальный текст
   и после подтверждения публикации поместить его в описание PR между маркерами.
3. Запустить `npm run release:prepare -- <номер-PR>` или Actions / Prepare release.
   Общая команда формирует notes и снимок подготовки, выполняет полный CI.
   Локально проверить diff и закоммитить материалы в той же ветке; Actions
   добавляет подготовленный коммит после проверок. Подготовка выпуск не разрешает.
4. При отдельном запросе на выпуск squash merge подготовленного release PR
   сохраняет версию и notes в main одной транзакцией. Release Please создаёт
   `vX.Y.Z` и draft GitHub Release. Job publish получает SHA и тег из outputs,
   делает checkout точного SHA, проверяет notes, собирает оба userscript-файла.
   Проверяются версия тега, metadata обоих файлов и наличие исполняемого JS.
   Полный lint/unit CI для тех же исходников в publish не повторяется.
5. Softprops v3 загружает оба точных файла, затем публикует draft с
   `RELEASE_NOTES.md`. `fail_on_unmatched_files: true`,
   `overwrite_files: false`. Stable assets: `sbg-vanilla-plus.user.js` и
   `sbg-vanilla-plus.meta.js`; прежние download/update URLs сохраняются.

Push тега и ручной workflow_dispatch выпуск не запускают.
Ручной bump, локальный тег, отдельный PR notes и обратный version commit не нужны.
Версия хранится в Git: например, после выпуска 0.16.0 main, тег v0.16.0,
локальная сборка этого SHA и опубликованные файлы содержат 0.16.0.
Между выпусками локальная сборка использует последнюю сохранённую версию.

## Настройки GitHub и миграция

- Разрешить только squash merge, squash title = **PR title**, тело = **PR description**.
- Защитить main: PR обязателен, enforce admins включён, required checks:
  `check` и `pr-title`. Боту не нужен обход защиты main.
- В Actions → General оставить default token permissions = read и разрешить
  **Allow GitHub Actions to create and approve pull requests**.
  Workflows выдают write только соответствующим jobs.

Эти настройки меняются через GitHub Settings/API, а не YAML.
GITHUB_TOKEN достаточно для release PR; App token/PAT для первого этапа не обязателен.
Ожидающее разрешения CI нельзя считать успешным.

Manifest начинается с 0.15.1; bootstrap SHA тега v0.15.1:
`31400e9ce1542b51506d39fb36ea6d711c268525`.
История до bootstrap не входит в новый выпуск. При подготовке первых notes
проверить также все non-conventional изменения после этого тега:
автоматический черновик может их пропустить.
При необходимости иной первой версии одноразовый `Release-As: X.Y.Z`
явно указать в описании миграционного PR перед squash. После миграции вернуться к автоматическому расчёту; перенос описания и соавторства сохраняется.

## Частичный сбой

Ошибка build/проверки/upload оставляет draft. После устранения причины выбрать
**Re-run failed jobs** или повторить только publish исходного run: он использует
сохранённые SHA и тег. Повтор всего workflow не равнозначен восстановлению:
Release Please может уже не вернуть `release_created`.

Перед ручным завершением проверить состав draft и уже загруженные assets.
Не перезаписывать их вслепую и не применять `--clobber`. При необходимости
собрать тот же SHA и ту же версию, проверить оба файла и завершить тот же draft.
Не перемещать тег и не повышать версию ради восстановления.

Создание release PR ботом, разрешение CI, фактическую публикацию и восстановление
publish проверять на GitHub при отдельно запрошенном выпуске.
Локальная проверка конфигурации и файлов не подтверждает эти внешние переходы.
